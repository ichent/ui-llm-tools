# UIKIT markup (index → исходники в репо)

## Правила

- Не выдумывать компоненты вне реестра.
- Не клонировать репозитории UI-KIT — только MCP.
- Не искать в `index.json`, читая весь файл в контекст — вызывать **ui-kit-paths**.
- MCP-серверы не вызывают друг друга; стыкует агент.
- **ui-kit-paths** только резолвит имя → `kit` + относительные `paths`. Про Bitbucket он не знает.
- Содержимое файлов брать через **отдельный Bitbucket MCP** (уже настроен), по соответствию kit → repo из конфига того MCP / пользователя.
- В `index.json` **нет API пропсов** — только имена, киты и пути к файлам.
- Несколько индексов / китов — нормально; формат может быть `v: 4` или `v: 5`. Опираться на поля, которые есть всегда (`importPath`, `title`, `type`). `exportName` / `componentPath` использовать только если они есть (обычно v5).

## Приоритет китов

При коллизии имён DF важнее Plasma (`UIKIT_KIT_PRIORITY` / порядок загрузки). Менять только если пользователь явно указал kit.

## Сценарий A — пропсы / API / примеры

Пример: «Дай свойства Divider» / «как использовать SearchInput».

1. `search_components` или `get_component` (ui-kit-paths) по имени компонента.
2. Если нет — сказать об этом; предложить близкие совпадения из поиска. Не выдумывать.
3. `get_source_paths` → `{ kit, paths, storiesPaths, componentPaths, … }`.
4. Bitbucket MCP: открыть репозиторий UI-KIT для этого `kit`, прочитать каждый path (сначала `storiesPaths` + `componentPaths`; если нет `componentPath` — stories и соседние component/types в той же папке при необходимости).
5. Достать пропсы из типов / props компонента / story `args` / argTypes.
6. Ответить в формате, который просил пользователь (таблица, список, пример JSX).

## Сценарий B — вёрстка по структуре компонентов

Пример: пользователь присылает дерево / структуру в духе Pixso с именами компонентов.

1. Для **каждого** уникального имени → резолв через ui-kit-paths. Неизвестное имя → пометить как unresolved / fake, API не выдумывать.
2. Для компонентов, которые реально рендерим → `get_source_paths` + Bitbucket MCP за пропсами и паттернами использования (хотя бы раз для незнакомого компонента).
3. Собрать JSX/TSX по заданной иерархии (родитель/дети, порядок, повторы).
4. Брать реальные импорты и пропсы из исходников; `TODO` только там, где в структуре нет маппинга.
5. При коллизии имён — приоритет китов, если пользователь не указал kit явно.

## Шпаргалка по tools

| Нужно | Tool |
|------|------|
| Найти / нечёткий поиск | ui-kit-paths `search_components` |
| Карточка + пути | ui-kit-paths `get_component` |
| Относительные пути + kit | ui-kit-paths `get_source_paths` |
| Содержимое файлов | Bitbucket MCP (отдельный; по kit и paths) |
| Какие киты загружены | ui-kit-paths `list_kits` |

## Антипаттерны

- Отвечать пропсы по памяти, не читая исходники через Bitbucket MCP.
- Считать `get_component` из ui-kit-paths полной документацией API.
- Ходить в Bitbucket до резолва компонента в index.
- Ожидать, что у каждой записи есть `componentPath` / `exportName`.
- Ждать `workspace` / `repo` / `ref` от ui-kit-paths — их там нет.
